## Context

The repository holds one Next.js 16 application at its root: twelve source files under `app/`, `components/`, and `lib/`, plus one route handler at `app/api/activity/route.ts` that already proves the pattern this change formalises — a server-side endpoint living inside the Next app rather than in a separate service.

Two forces make a workspace worth the disruption now.

The ENSv2 spike is a script. It has no HTTP server, it runs before any UI exists, and it must share exactly one implementation of `EnsService` with the route handlers that come later. If the spike is written flat and the product re-implements the same calls, the two drift, and `docs/17_RISKS_AND_FALLBACKS.md` Risk 1 explicitly asks for ENS integration behind a single boundary so that beta interface churn has one place to break.

The second is credential separation. `docs/19_ENV_AND_CONFIG.md` lists roughly twenty variables, several of which — the Privy app secret, the Privy authorization private key, the Graph API key, the organization signing key — must never reach the browser. A package boundary plus `server-only` turns that from a review-time discipline into a compile-time error.

The principal chose Next route handlers over a separate service, and chose to scaffold everything now rather than after the Day 1 gate.

## Goals / Non-Goals

**Goals:**

- One implementation of each integration, importable by both a script and a route handler.
- A dependency graph that makes server-only code impossible to import from the client.
- Task caching that is correct in the presence of many environment variables.
- File history preserved across the move, so `git log --follow` still works on the landing page.
- A layout that can absorb a standalone service later without relocating domain logic.

**Non-Goals:**

- A second HTTP server. Route handlers are the backend.
- Publishing any package to a registry. Everything is `private: true` and consumed through `workspace:*`.
- Build outputs for packages. They ship as TypeScript source.
- Changing any behaviour of the existing landing page. This is a move plus scaffolding, not a rewrite.
- Docker, CI pipelines, or deployment configuration.

## Decisions

**D1: Next.js is the backend; no `apps/api`.**
Every secret-bearing operation in the PRD is request-scoped: read ENS state, grant a permission, query Agent0, execute a Privy payment. Route handlers run in Node with full access to secrets, and one already exists in the repository. *Alternative considered:* a Hono or Express service in `apps/api`. Rejected because it doubles the deploy targets, adds CORS and a second environment surface, and contradicts `docs/04_SYSTEM_ARCHITECTURE.md`. The cost of being wrong is low: packages hold the logic, so a future service imports them unchanged.

**D2: Packages ship TypeScript source, not compiled output.**
`exports` points at `src/index.ts`. Next consumes them via `transpilePackages`; scripts run through `tsx`. *Alternative considered:* `tsup` builds with `dependsOn: ["^build"]`. Rejected for this project because it inserts a build step into every dev iteration and every spike run, for a benefit — consumable by non-TypeScript tooling — that nothing here needs. The trade is that type errors inside a package surface at the consumer's typecheck rather than at its own build, which the per-package `typecheck` task covers.

**D3: Every environment variable is declared in `turbo.json`.**
Turborepo hashes only the variables it is told about. With roughly twenty of them, an undeclared `ENSV2_PARENT_REGISTRY_ADDRESS` would mean editing an address and receiving a cached build compiled against the old one. That failure is silent and would be debugged as a contract problem. `globalEnv` covers what affects everything; per-task `env` covers the rest; `globalDependencies` includes `.env.example` and `tsconfig.base.json`.

**D4: `server-only` at every server package entrypoint.**
The package is already a dependency. Importing `@nymspace/privy` from a client component becomes a build error rather than a bundle containing `PRIVY_APP_SECRET`. `@nymspace/core` is split so that pure types and the ERC 7930 encoder stay importable from anywhere, while `serverEnv` sits behind the guard.

**D5: Path aliases stay local; packages resolve by name.**
`@/*` remains defined only in `apps/web`, so nothing inside the app changes when it moves. Packages import each other as `@nymspace/core`, never through a relative or aliased path. *Alternative considered:* a root-level alias map covering every package. Rejected because it produces two ways to name the same module and breaks any tool that resolves through `package.json` rather than `tsconfig`.

**D6: Move with `git mv`, in one commit, with the `AGENTS.md` fix included.**
`AGENTS.md` is regenerated by `next dev` from `node_modules/next/dist/server/lib/generate-agent-files.js`, resolved relative to the Next package. After the move it will be written at `apps/web/AGENTS.md`, orphaning the root copy that `CLAUDE.md` imports. Doing the move, the regeneration, and the `CLAUDE.md` import fix in one commit keeps the tree clean, which is what `AGENTS.md` itself advises.

**D7: The spike lives in `packages/ens`, not in a root `scripts/` directory.**
It is ENS-domain code that imports `EnsService` from the package it sits in, and it becomes `pnpm --filter @nymspace/ens spike`. A root `scripts/` directory would sit outside the workspace graph and outside Turborepo's task model.

## Risks / Trade-offs

- **This lands before the Day 1 ENSv2 gate and competes with it** → `docs/14_EXECUTION_PLAN.md` reserves Day 1 for proving the permission model, and U1 through U3 are unstarted. Mitigation: the scaffold is mechanical and bounded; if it exceeds half a day, stop, land what exists, and go straight to the spike. The workspace is useful half-built; the gate is not.
- **`transpilePackages` misconfiguration produces confusing Next errors** → A missing entry surfaces as a parse error in `node_modules`, not as a clear message. Mitigation: add all four packages at once, and verify with a trivial import from `apps/web` before writing real code.
- **A stale cache from an undeclared variable would be debugged as a contract bug** → The most expensive failure mode in this change. Mitigation: D3, plus a task that diffs the declared set against `.env.example` so the two cannot drift.
- **Moving the app breaks tooling that assumes a root Next app** → `components.json`, `postcss.config.mjs`, and the Tailwind v4 setup all resolve relative to the app. Mitigation: move them together with the app rather than leaving them at the root, and run the dev server before committing.
- **Two changes touch the same files** → `ensv2-authority-spike` claims `scripts/spike-ensv2.ts` and a root `.env.example`. Mitigation: this change lands first and that change's section 1 is rewritten as part of it, rather than leaving two proposals describing incompatible layouts.

## Migration Plan

1. Enable the workspace in `pnpm-workspace.yaml`, keeping `ignoredBuiltDependencies`.
2. `git mv` the application into `apps/web`, including its configuration files.
3. Add `tsconfig.base.json` and point `apps/web/tsconfig.json` at it, keeping `@/*`.
4. Add `turbo.json` and root scripts.
5. Create the four packages as empty typed shells with `server-only` guards in place.
6. Run `pnpm install`, then `pnpm dev`, and confirm the landing page and `/api/activity` still work.
7. Commit the move, the regenerated `apps/web/AGENTS.md`, and the `CLAUDE.md` import fix together.

Rollback is `git revert` of a single commit. No published artifacts, no external state, nothing deployed.

## Resolved Questions

- **Where the ERC 7930 encoder belongs — resolved: `@nymspace/core`.** The open question's criterion was consumption: only `@nymspace/ens` builds ENSIP 25 keys, so the encoder should move there. That criterion misses the guard. `@nymspace/ens` is behind `server-only`, so moving a pure, secret-free helper into it would make it unreachable from any client-side manifest rendering — and `docs/06_AGENT_IDENTITY_STANDARDS.md` describes the Manifest as a UX surface over exactly these keys. The cost of leaving it in `core` is one small module in a package that already exists; the cost of moving it is a second copy the first time the browser needs to parse a registration key. It stays in `core`, and `packages/ens/src/keys.ts` imports it by package name.

- **Whether `@nymspace/graph` and `@nymspace/privy` should exist yet — resolved: yes, with real boundaries rather than empty shells.** Each holds the types and the client boundary its day of work needs, and neither implements a call it could not verify. The `server-only` guard on both is the load-bearing part and is proven: importing `@nymspace/privy` from a client component fails the build with the import trace running through `packages/core/src/env.ts`.

- **Test runner — resolved: Vitest.** Chosen over `node:test` for its assertion surface and watch mode, and over Jest because nothing here needs Jest's ecosystem and Vitest reads TypeScript source without a transform step, which is the same property that lets these packages ship source. Wired at the workspace root, with `test` scripts in `@nymspace/core` and `@nymspace/ens`. The `test` task in `turbo.json` now runs fourteen tests over the pure helpers `docs/13_TEST_PLAN.md` names — ERC 7930 round-trips, DNS wire encoding, and ENSIP 25 key construction, negative cases included.

## Open Questions

- **The ENSIP 25 registry form.** `agentRegistrationKey` takes a `registryForm` argument because the draft does not pin whether the registry component is the binary interoperable address or its text form. The Day 1 spike resolves it against the deployed resolver, and the argument collapses to a constant once it does.
- **The EAC resource derivation.** Left as an injected `ResourceDeriver` port rather than guessed. `docs/05_ENSV2_IMPLEMENTATION.md` says to compute the record resource through the current contract helper path, and a wrong derivation returns `false` from every role check with nothing in the logs to explain why.

## Timebox Outcome

The scaffold was to stop and land what existed if it exceeded half a day. It did not: the move, the shared configuration, the Turborepo pipeline, the four packages, and every acceptance check in section 6 landed well inside that budget, so the Day 1 ENSv2 gate is not delayed. `packages/ens` is a real boundary rather than an empty directory, which is the part the spike immediately builds on.
